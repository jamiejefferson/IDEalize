# Agent Note: pi-ai 0.85.1 — GPT-6 Astra reaches both OpenAI routes, and a pre-dispatch abort still reads as a cancel

Status: implemented

JJ, 8 Sep 2026, reading the report that no provider catalogue carried the model: "It should be available in oauth, perhaps not in api." The [provider-names note](2026-09-08-provider-names-and-model-prices.md) explained the absence on screen; this note moves the catalogue so the model is there.

## Problem

The harness serves OpenAI's model list from the `@earendil-works/pi-ai` catalogue the app ships (`packages/llm/llm-pi-ai/src/catalog.ts` reads `getBuiltinModels`; `@idealize/models` lists `openai-codex` through `ctx.llm.listModels`). The pinned 0.82.1 stopped at `gpt-5.6-terra`. pi-ai 0.85.1 lists `gpt-6-astra` under `openai` (API key, `openai-responses`) and `openai-codex` (ChatGPT OAuth, `openai-codex-responses`), with efforts `low` through `max` and text-plus-image input. Moving the pin surfaced four drifts in the adapter's tests and two compile errors, each a fact about pi-ai that changed rather than a defect in the adapter.

## Decision

`@earendil-works/pi-ai` is `^0.85.1` in `llm-pi-ai`, `@idealize/provider-pack`, `@idealize/services` and the workspace's `minimumReleaseAgeExclude`. The changes in 0.85.1 that the adapter depends on, read from the published `dist`:

- **Abort before dispatch is reported as an `error` stop.** `Models.streamSimple()` resolves the route's auth under the request signal (`auth/resolve.js` wraps `resolveProviderAuth` in `raceWithAbortSignal`; new `utils/abort.js`). An already-aborted signal rejects that step, and `api/lazy.js` turns a setup rejection into an `error` event with `stopReason: 'error'` and the abort reason as `errorMessage`. Only an abort that interrupts an open request still arrives as `stopReason: 'aborted'`. The adapter now hands the caller's own signal to `toStreamChunks`, which reads an `error` finish under an aborted caller signal as `kind: 'aborted'`, code `ABORTED`. This is the same precedence the adapter already gave a thrown error under an aborted signal, so a cancel never reaches the agent loop as a provider failure whichever path pi-ai takes. The watchdog's signal is excluded so idle expiry still surfaces as `TIMEOUT`.
- **DeepSeek requests carry `max_tokens`.** The catalogue entry pins `compat.maxTokensField: "max_tokens"` and the URL detection in `api/openai-completions.js` agrees. A caller's `maxTokens` still reaches the provider; the adapter test asserts the new field name and the absence of `max_completion_tokens`.
- **`StopReason` gains `pending` and `deferred`.** `pending` is the pre-terminal state and `deferred` answers a deferred-response request the adapter never makes. `mapStopReason` fails either on a terminal event with `PI_AI_ERROR`, naming the stop and the model, which keeps the closed-union switch exhaustive.
- **`thinkingFormat` gains `baseten`.** It drives the request through `chatTemplateArgs`, which the profile schema does not expose, so it joins the withheld formats beside the two `chat-template` spellings and the drift gate compiles again.
- **Catalogue data.** DeepSeek V4 Flash offers `low` (`['off','low','high','max']`); xai ships every model as `openai-responses`, so the mixed-route compat test now takes the first installed provider spanning `openai-completions` and `openai-responses` (four do in 0.85.1) instead of naming one.

A catalogue test lists `gpt-6-astra` through `ctx.llm.listModels` on both routes and checks its six efforts through `resolveModelInfo`.

## Alternatives considered

- **Adding `gpt-6-astra` to the OpenAI routes by hand in settings.** A hand-declared model carries none of the catalogue's compat flags (`supportsToolSearch`, `supportsExplicitPromptCacheMode`, the effort map), and the id would go stale the moment OpenAI renames it. The catalogue is the one place the app already reads.
- **Mapping the pre-dispatch abort by message text** (`errorMessage === signal.reason`). The reason is whatever the caller passed to `abort()`, often `undefined`; the signal's own `aborted` flag is the fact the mapping needs and is what the thrown-error path already checks.
- **Loosening the tests to accept either finish kind.** The agent loop branches on `aborted` against `error` to decide between silence and a retry prompt; the tests describe that behaviour and it has to hold.
- **Naming another mixed provider in the compat test.** `opencode` or `github-copilot` would break on the next catalogue reshuffle the way `xai` did; searching for one keeps the test's intent (a real catalogue spanning two protocols) without the drift.

## Consequences

- The Brains picker lists GPT-6 Astra under OpenAI and OpenAI (ChatGPT) on the next launch that ships this build; the built-in count on the OpenAI route moves from 38 to 39 models.
- `subscriptionModel` in `packages/idealize/models/src/policy.ts` reads its flagship from `FLAGSHIPS` (`gpt-6-astra`, then `gpt-5.5`), so auto in its intelligence tier selects the newer model on a route that carries it (JJ, 8 Sep 2026: "update the auto policy to prefer gpt-6-astra"). The route's ids do not order themselves — `gpt-6-astra` sorts below `gpt-5.6-terra` — so the list is what puts the newest first; a route carrying neither falls back to its first non-mini id, and the speed tier still prefers a mini, of which `gpt-6-astra` has none.
- `toStreamChunks(events, contextWindow, callerSignal?)` gains an optional third parameter; existing callers and tests pass two arguments unchanged.
- Tests: `llm-pi-ai/tests/convert.spec.ts` (error stop under an aborted caller signal, error stop under a live signal, `pending` and `deferred` as failures), `adapter.spec.ts` (`max_tokens`, DeepSeek `low`), `catalog.spec.ts` (GPT-6 Astra on both routes, DeepSeek `low`, mixed-route provider search).
