# Agent Note: First-run onboarding wizard, step bodies, and the rainbow burst

Status: implemented

## Problem

IDEalize's first run asks more of the user than [the setup flow](../../implemented/feature/2026-08-24-idealize-first-run-setup-and-folder-aliases.md) covers: connect agents, pick tool models, choose both folders, and land oriented — as a friendly five-step wizard with per-step skip, skip-all, and a celebration per completed step, replacing `@idealize/setup`'s card-based client overlay. Nothing about that wizard existed: no step vocabulary, no durable record of per-step outcomes, no full-screen surface for it, and no celebration primitive anywhere in the client.

## Decision

**One package, two faces, `@idealize/setup`'s topology.** `@idealize/onboarding` splits host and client exactly like setup: `tsconfig.host.json` carries `src/index.ts` + `src/routes.ts` + `src/invariant.ts` into the Host aggregate, `tsconfig.client.json` carries `src/client/*` into the Client one, and `tsconfig.json` is the two-project solution. The host half owns the `idealize-onboarding` settings section and the two agents routes; the folder/finish work reuses `@idealize/setup`'s routes rather than growing new ones.

**The section is `{ done, steps, completedAt? }` with validated step keys.** `steps` is a `z.dict` whose key schema is the step-id union (`agents | tools | projects-folder | documentation-folder | finish`), so a hand-edited `settings.yaml` naming an unknown step fails the registration — misconfiguration fails loud at the earliest point. The `OnboardingSettings` interface rides the schema's full-key `Record` type (schemastery's dict static type), with the sparseness documented on the field: a step with no key is untouched. The step vocabulary lives in `src/step-ids.ts`, a pure leaf both faces compile — the client machine imports it relatively, so the client program never pulls the host face's imports in, which is the contamination the split-face layout exists to prevent.

**Claude Code detection reuses the subprocess seam; the OpenRouter save is verify-then-store.** `GET /idealize/onboarding/agents` resolves `claude` through `ctx.subprocess.resolveExecutable` — the same call subagent-claude-code starts runs with, whose miss throws, so detection is resolve-and-catch — and reads OpenRouter presence from `credentials.resolve`. `POST /idealize/onboarding/openrouter` verifies the typed key against OpenRouter's models listing before anything persists (a rejected key stores nothing), then stores the credential and writes the `openrouter` provider route's `apiKeyEnv` binding into the `llm-pi-ai` section. That profile write is the whole configuration: `openrouter` is a pi-ai catalog provider — dormant but listed in `listConfigurableProviders()` before any route exists — so without the binding the route would fall back to pi-ai's ambient env discovery and never see the stored key. The verification endpoint is a `Config` field (`openrouterBaseURL`, defaulting to the public API), which is what lets the composition test stand a local server in for OpenRouter.

**The step machine is pure; the flow controller is cordis-free; the wire mapping is a fetch layer.** `src/client/steps.ts` holds `deriveStep` (first unresolved step, null when done or fully resolved), `advance`, `skipAll`, and `stepBefore` — no React, no services. `src/client/flow.ts` holds `createOnboardingFlow(deps)`: the view store, the resolved-outcomes mirror (the settings scope's snapshot lags the wire, so the flow accumulates `steps` itself and persists the whole map per write), and every overlay action. `src/client/api.ts` holds `createOnboardingApi(fetchFn)`: the typed fetches over the wizard's own routes plus the existing `/idealize/models/state`, `/idealize/activity/*`, `/idealize/brains/media`, and `/idealize/setup/*` routes, including the provider filter (`models.length > 0`) and the wizard's six-row selection (JJ's list omits Writing and Sound). The plugin closure in `src/client/index.ts` only binds these to the scope, the tour hold, and the inject face. This split is what lets the specs drive the real controller and the real wire mapping over a mock fetch, not mocked twins.

**Step bodies own a gate and a commit; the overlay owns the chrome.** A body (`AgentsStepBody`, `ToolsStepBody`, `FolderStepBody`, `FinishStepBody`) receives the api face plus two callbacks: `onReadyChange` gates the overlay's Continue (the agents step disables it until Claude Code or OpenRouter connects; a folder step engages it only after a successful probe of the current path) and `registerCommit` hands Continue the body's save action (the tools step saves only user-changed rows — stored choices pre-select, so untouched rows keep their defaults without a write — and a failed save is named against its row and blocks completion; the finish step's commit runs the orientation). The overlay resets both during render on a step change: an effect would fire after the freshly mounted body's own effects and clobber what it just registered. The agents step registers no commit — connections persist at connect time. LLM activity saves round-trip the preset's current `instructions`, because `/idealize/activity/agent` replaces the persona with its generic template when the field is absent.

**The tools step groups six unique choices by space.** Chat and Terminal share Design, Coding, Admin and Free, so one model choice configures each shared brain once. Gallery renders the stored `images` row and Motion renders `motion`; their labels follow the [space vocabulary](../architecture/2026-08-26-idealize-spaces-vocabulary.md). The stored ids remain unchanged. Writing and Sound remain in the [Brains pane](2026-08-26-brains-pane-grouped-by-space.md). Each unavailable media row uses the live `/idealize/brains/media` verdict to select the same localised recovery sentence as the launcher and Brains pane. A `no-compatible-model` verdict also offers “Add OpenRouter key” and returns to an editable field on the Agents step, including when a key already exists. Returning to Tools reloads availability and retains unsaved choices in the overlay. A `no-backend` verdict carries no key action because a credential cannot install an adapter.

**The folder steps probe through the alias route and pre-fill from setup's aliases.** `POST /idealize/setup/alias` is the only live probe the host offers, so a successful probe also persists the alias (orientation re-confirms both at finish; a wizard abandoned between a folder step and finish keeps the probed alias — recorded in the README's limitations). A second `settingsScope.bind({ namespace: 'idealize-setup' })` pre-fills each folder from the existing aliases, so a returning user confirms in one tap. The finish step calls `POST /idealize/setup/orientation` with both folders and the optional first-project name (locale default, omitted when emptied), renders a 400's per-field refusals verbatim, selects the created project through `ctx.workspaces.startSession`, and only then completes the flow. The Settings re-run row is a `settings.general.item` occupant resetting `done`/`steps` — the gate decides once per session, so the wizard re-arms on next launch.

**The owl is JJ's per-step clip, inlined.** `src/client/owl-clips.ts` (generated by `scripts/gen-owl-clips.ts` from the out-of-repo WebM sources, splash-frames precedent) carries the five transparent clips as data URIs; `OwlArt` plays the step's clip (`muted loop playsinline`, parked on its first frame under reduced motion) behind the same `data-owl-art` hooks. Inlining ~630KB beats adding an asset route for five files; the README records the trade.

**The wizard is an opaque surface, not a scrim.** The `shell.overlay` occupant (`idealize-onboarding`, order 95, z 50 over the tour's 40) paints `position:absolute; inset:0` with the solid `--dsw-alias-bg-base` ground — the app disappears behind it rather than dimming. Each step renders the placeholder owl (`OwlArt.tsx`, an inline geometric SVG keyed `data-owl-art` per step for the later art swap), a headline and one-line sub in en+zh, a `data-onboarding-body` hook the step bodies fill, five progress dots, Back (hidden on the first step), a per-step "Skip this step" link (omitted on finish, where it would duplicate "Skip setup"), and the persistent top-right "Skip setup".

**The burst is CSS-only motion behind a data contract.** `RainbowBurst.tsx` renders three expanding conic-gradient rings (masked to rims) over a soft radial flash, all pure keyframes over ~800ms, on a `pointer-events: none` layer above the wizard, plus a `role="status"` toast line per completed step. It fires on completions only — skips advance quietly. The `prefers-reduced-motion` decision is made in JS (`matchMedia`, injected as `prefersReducedMotion()` so tests drive it) and renders a static tint instead of the rings; a CSS `@media` block independently kills the animations if the two ever disagree. The component owns its lifetime and reports it through `onDone`; the finish step's completion marks `final: true`, and the flow closes and releases the tour hold when that last burst ends, so the celebration is seen, not cut.

**Tour sequencing copies setup's hold pattern verbatim.** `ctx.tour.holdFirstRun()` at plugin start, `releaseOnce` guard, and a dispose effect; the release happens on exactly four paths — seed already closed, settings unavailable (a remote browser keeps preferences process-local and onboarding is a Host concern), skip-all, and the final burst's end. Setup's client overlay — the pattern's origin and this wizard's `shell.overlay` twin — retired once the wizard covered its steps; setup is a host-only seam now, and its note tracks the move.

## Alternatives considered

**Sharing the step vocabulary through the host face's types.** The brief sketched the client importing the step-id union type-only from `@idealize/onboarding`. Type-only still drags `src/index.ts` — and with it schemastery, `dsh-settings`, and their host-side merges — into the Client program, the exact contamination setup's split faces refuse. The `src/step-ids.ts` leaf gives both faces one source with zero imports.

**Driving the overlay spec through a stubbed action face, like setup's spec.** Setup's overlay test asserts its stubs were called and trusts the plugin closure. That leaves "skip writes state" and "finish writes done + completedAt" — the behaviours this package exists for — untested. The cordis-free flow controller costs one small module and puts the whole state machine under the jsdom spec.

**Playing the finish burst over the app after closing.** Closing first and bursting after would unmount the burst with the overlay; keeping the finish step on stage beneath the final burst and closing on `celebrationDone` preserves the finale at the price of holding the surface ~800ms longer.

**Writing a full provider profile, like freetokens' `registerRoute`.** Freetokens declares `api`/`baseURL`/`models` because its sidecar is a route pi-ai has never heard of. `openrouter` is a pi-ai catalog provider, so the profile needs only `apiKeyEnv` — anything more re-states the catalog and can drift from it. The verify-then-store order (never persist a failing key) is shared; the profile content is deliberately not.

**Lifting the step bodies' state into the flow controller.** The flow is cordis-free precisely so specs drive it without cordis machinery; adding per-step fetch state would bloat it into a second api layer. Bodies keep their own component state and report the two things the chrome needs — readiness and a commit — through callbacks, which keeps the overlay spec's seam identical to production.

**Separate Chat and Terminal copies of the same brain controls.** Both copies would write the same stored model and could show two controls for one decision. One shared group states that the four brains work in both spaces and keeps each saved choice unique.

## Consequences

First run now has its own durable record (`idealize-onboarding.done/steps/completedAt`), separate from `idealize-setup`'s component seeds, and owns the whole first-run surface: `@idealize/setup` is the host-only seam behind it (aliases, probes, orientation), its note cross-linked. A relaunch mid-flow resumes on the first unresolved step; the Settings row re-arms the flow for the next launch. The client slot catalog is regenerated for this tree; `@idealize/ui-launch` lands from its own worktree and the combine regenerates the catalog once more to include it.

The tools grouping changes no persistence or save request. Activity rows still omit `spaces`, which preserves the placement the Brains pane owns. The user sees Gallery, and `images` remains the media route's stored id. Draft retention lasts only for the open wizard; a relaunch still derives every pre-selection from the stored route state.

There is no assembled-application snapshot lane for this flow — no model-visible input, no session events — the jsdom specs stand in, as with setup. The host composition test boots a real settings document and web server with only machine facts stubbed (credentials, the PATH lookup, and a local stand-in for OpenRouter); the tools step's persistence goes through the pre-existing activity-pills and generate routes, which carry their own coverage. Rendered proofs (each step in both themes, the burst mid-frame, reduced motion) and the packaged-window pass land with the verification piece.
