# Agent Note: Wave E — one Studio for every project, posted through the ordinary composer

Status: implemented

JJ's 3 Sep feedback after landing 6, items 1 to 5 and 7 of `.idealize/plans/feedback-wave-e-plan.md`. Item 6 (fal.ai as a media provider) follows in its own note.

## Problem

Landing 6 gave each project its own Studio chat, so the pinned card named one project and the view read one project's timeline; JJ wants the Studio to watch every project. The Studio view rendered its own `<input>` plus Send instead of the composer every other view has, so attach, brain and the `@` menu were missing, and nothing autocompleted agent names. The Askbar showed "ID" where the IDEalize mark belongs and set its chips 12px apart, which JJ read as cramped. The Brains rail entry drew a brain; JJ asked for a sparkle.

## Decision

- **One Studio chat overall** (`@idealize/ui-bar`). `studioChat()` finds the first `studio`-space chat in any project; `openStudio()` opens it or mints one in the first listed project. The card's subtitle was V0's "Watching every project's agents" (replaced by the Telegram status line on 15 Sep 2026: [Studio card — the Telegram status line](../feature/2026-09-15-studio-card-telegram-line.md)), its dot is green while the overview answers, its count sums unresolved attention across projects, and any `open-studio` bridge event opens it. `POST /idealize/askbar/transform {open:'studio'}` no longer needs `project`; the field is context only.
- **`GET /idealize/studio/overview`** serves every stored project's `{project, lastSeq, state (+presence), recent}` in one read; the view and the card poll it instead of per-project state and timeline routes. The view lists each project under its own heading with a merged timeline row tag.
- **The Studio chat posts through the ordinary composer.** `@idealize/studio` listens on `agent/pre-step`: for a `studio`-space session it takes the user-sourced text (`source.kind === 'user'`, so `@idealize/comm`'s injected name notice never counts), hands it to `postFromChat` and returns `{kind:'reject'}`, so the turn ends `blocked` and no `user/message` is logged. `@Name` (longest match on agent name, task title or session id at a word boundary among every project's participants) delivers to that one agent on its project; an unaddressed post is recorded on every stored project and every present participant's project, one record per project keyed `<messageId>:<projectKey>`; an unresolved or ambiguous `@` records nothing and pushes a bridge `notify` naming who is present. The view root declares `data-conversation-composer-overlay` so the composer seat sits at the bottom and the body clears `--dsh-composer-height`; `HeroLauncher` treats the `studio` space as launched so the welcome chooser never appears in that seat.
- **The Studio chat is not an agent.** `@idealize/comm` leaves it out of `roster` (live via `foldSpace`, cold via the projection cache) and skips naming it at session start.
- **An `@` source "Agents"** (`@idealize/ui-studio`, order -1) lists every named chat across projects with the project folder as hint and inserts `@Name `. It is registered for every chat because an addressed message from any chat is a valid delivery.
- **Askbar mark and spacing.** `BrandMark` at 44px replaces "ID"; chips sit 20px apart.
- **Brains glyph.** `BarIconModels` is a four-point sparkle with a companion star.

## Alternatives considered

- Keeping one Studio chat per project and letting the card switch between them: JJ's words were "for all projects", and a per-project Studio put the coordination view behind a project pick.
- Sending Studio posts from the view through its own route, as before: the point of item 4 is the ordinary composer, whose only sink opens a turn; intercepting the turn on the host is the one seam that keeps the composer intact.
- Routing an unaddressed Studio post to a "current" project: the Studio has none, so a broadcast is the only honest landing.
- A separate model-free session kind for the Studio: heavier than a space plus a pre-step reject, and the space already exists.

## Consequences

- `SessionEventMap` is unchanged; a Studio post leaves a `blocked` turn and no `user/message` in the chat's log, and the timelines hold the record.
- `StudioComposer.tsx` and its spec are gone; `ProjectView`, `OverviewResponse`, `StudioOverviewProject`, `StudioChatPost` and `resolveAddress` are new exports, the latter two exempted in `gen-cordis-catalog`.
- `@idealize/studio` now depends on `@idealize/spaces`; `@idealize/comm` on `@idealize/spaces` and the projection cache; `@idealize/ui-studio` on ui-input-trigger and `@idealize/comm` (types).
- The Studio chat's header still shows the default brain; cosmetic, unaddressed.
- Proof: `studio-proof.mts` (card label "Open the Studio", the composer seat present, the `@` menu offering a chip's name, a delivered post on the timeline, both themes).

## Follow-up (landing 7 walk): the first step waited on bookkeeping

The packaged walk's Studio post never landed within 20s: `session-checkpoint-policy` awaits `ctx.sessions.flush(session)` on every pre-step, `session/flush` is parallel-mode (every listener awaited), and `@idealize/vault` (a git read in the project, which can sit behind the live app's index lock) and `@idealize/doc-policy` (a full documentation-folder scan) both held it on a session's first flush. Headless probes over the walk's data measured 20s+ on some runs and ~1s on others. Every chat's first step paid this, not only the Studio's. Both listeners now run their work detached and settle it at their plugin's disposal, so the flush waits for persistence alone and a final flush before teardown still lands the evidence (`doc-policy/tests/composition.spec.ts` proves the flush returns while a scan is held and disposal waits for it).
