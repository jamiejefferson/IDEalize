# @idealize/askbar

The Askbar's A1 prototype: the screen-edge agent dock of the Askbar/Studio release plan (`.idealize/plans/askbar-plan.md`), built to the design spec (`idealize-askbar-design-spec.md` in JJ's vault, 1 Sep 2026). The host half serves the roster the bar renders from, the transform route into the desktop shell, and the still owl for the Studio tile; the browser half is one rail in two homes: the whole surface of the desktop Askbar window, and the main sidebar's collapsed column. The `idealize-askbar` row in `@idealize/bundle-idealize` mounts it.

## The roster

`GET /idealize/askbar/roster?project=<folder>&sessions=<id,id>&all=1` answers everything the bar renders in one read: the interaction timings from config, plus one chip per chat. `all=1` adds `groups`, one entry per project, each carrying that project's folder, its display name and its own chips — both rails show every project's agents at once (JJ, 10 Sep 2026), so both ask for them. With `sessions`, `assembleGroupsOf` (pure) groups exactly those chats by their project, in the order sent, so the rails carry the expanded sidebar's rows and nothing comm names beyond them (JJ, 13 Sep 2026: the blank chats comm still names had been showing as agents); without `sessions`, `assembleGroups` (pure) groups comm's whole listing. A grouped read costs one listing, one board with no path and one Studio overview however many projects there are, and it lists even when this window names no project; a chat belonging to no project joins no group. `sessions` names the chats to cover, in order; the bar sends the main sidebar's rows, so the three sidebar states show the same agents in the same order (JJ, 8 Sep 2026). A session comm does not list contributes no chip: the Studio chat, which comm treats as the person's own seat, and any session comm has not seen. Without `sessions`, every comm chat whose `projectPath` is the folder is covered. An empty `project=` (a window opened before any project exists) gets the timings and no chips, never an error; only an absent parameter 400s. The join (`assembleChips`, pure) reads two probed sources and degrades honestly when one is absent:

| Source | Contributes | Absent |
|---|---|---|
| `idealizeComm` `list` + `board` | chat identity (id, name, title, role), `running`, unread, status label, rung blockers | an empty roster |
| `idealizeStudio` `state` | the displayed task's goal, execution and attention states | comm-only states; `task` stays null |

`GET /idealize/askbar/owl.webp` serves `@idealize/skin`'s `OWL_FRAME_STILL` (the splash run cycle's first frame) as an immutable WebP, so the client bundle carries no image data.

## Which chats the bar shows

`selectEverything` (`src/client/selection.ts`, pure) lists what the expanded sidebar shows, in its order: each workspace's first five rows (`GROUP_ROW_LIMIT`, the sidebar's cap before its Show more control, which resets whenever the sidebar remounts) in the order the sidebar renders, then the first five rows outside every workspace, minus archived sessions, subagent children, Studio chats and blank rows other than the current one (the sidebar shows that one as New Session). The rendered order is the sidebar's persisted order with its own promotion applied: under `updated` ordering a row touched since the sidebar last synced moves to the front, newest first, and an account never synced is wholly newest first, which is what the sidebar does the moment it mounts. The sidebar persists its ordering, order and last-seen activity in ui-workspace's view store (`dsh.workspace.view.v5` in localStorage) and the main window its open chat in the selection store (`dsh.sessions.current`); the floating bar is a second page on the same origin, so `readSidebarOrder` and `readCurrentSession` (`src/client/sidebar-order.ts`) read both entries and the plugin re-selects on the page's `storage` event. The project the selection names is the one `selectRoster` follows: the current session's workspace, then the most recently touched accounted session's, then the first; a current session outside every workspace names its folder. The client plugin subscribes to both runtime stores, so when the main window moves to another project the bar follows at once: the store refreshes immediately and, on a project change, drops the old roster rather than show another project's agents for a poll cycle.

## Chip states

`chipStateOf` folds the signals into the visual states in this order: `wrong` (failure attention, failed execution, or a stuck rung), then `needs-input` (user-owed attention or a waiting-on-user rung), then `working` (comm's `running`, true only while the agent runs a turn, or a working terminal CLI; a live agent whose Studio task is still `working` also counts), then `ready` (comm's `live`: an agent holds the session and waits between turns), then `idle` (a cold chat). Working is what animates the chip's orbit ring; before 15 Sep 2026 the fold took working from a Studio task alone, so a plain chat answering read Ready with a still dot (JJ: "the green circle doesn't signify 'working'"). Attention outranks the rest because an owed answer is owed whether or not the agent is loaded, and the Studio shows the same attention until it is resolved. `idle` replaces the design spec's `disconnected` (JJ, 8 Sep 2026: the old label read every quiet chat as broken): a chat with nothing running and nothing owed is idle, comm's own status word for it; only the host can be unreachable, and that is the bar's error state, not a chip state. `listening` is client-local — a held capture — and never appears in a roster.

## Portraits

`portraitOf(project, name)` renders the decided kaomoji portrait (design spec Option A): a deterministic seed of project plus agent name picks eyes, mouth and bracket from small fixed sets, plus a pastel chip fill, so the same agent shows the same face everywhere and no image asset exists. Exported from the package root so later surfaces (Studio messages, thread headers, notifications) render the same identity.

## One rail, two homes (browser half)

`Rail` (`src/client/Rail.tsx`) is the bar body, and it renders in two homes (JJ, 8 Sep 2026, review item 26: "collapse sidebar vs minimode — aligned/combined"). Both homes run the Studio entry (a small owl in a circle), a rule, then the chips in a scrolling column (overflow scrolls — nothing pops out). The floating home puts the IDEalize mark over the project name above that; the sidebar home does not, because the sidebar column already carries the logo and the New-chat control above the seat. Arrows move between chips, Enter opens the compact panel, Escape closes or discards, and hovering a chip for `hoverRevealMs` reveals its panel until the pointer leaves. The rail element carries `data-askbar-rail` and `data-home` (`floating` or `sidebar`) in both homes. One store feeds both: it polls the roster (interval from config) and hurries on any host-bridge SSE event, so `agent-finished` and mail land without waiting for the poll.

**The floating home** is the desktop shell's Askbar window. The plugin gates on the `dsh-desktop-mode=askbar` window marker, marks the page, and registers `AskbarRoot` into the root slot at priority -1, so the bar replaces the whole app frame there. The root (`data-askbar-bar`) draws the 72px column with `BrandMark` at the sidebar's 58px under the sidebar's 16px top inset and 20px between chips; its background is the window's drag region (`-webkit-app-region: drag`), and every button, field and dialog opts out, so a press on a chip is a press. The desktop shell remembers where a drag leaves the window. The project cell grows back to the main window through the transform route; the Studio entry and the panel foot also ask it for the Studio chat.

**The sidebar home** is every other window. The plugin registers `SidebarRail` into the main sidebar's `sidebar.rail` seat (`@deepseek-ai/dsh-client-ui-sidebar`) once the sidebar declares it, and the shell renders it in place of the project browser's icon column while the sidebar is collapsed, so the collapsed sidebar shows what the floating bar shows. The rail lays out for the collapsed column's 36px content width: the owl and every agent circle at 36px so the faces read at 13px, each circle carrying its agent's name under it, the empty and error lines hidden (the column cannot hold a sentence), 12px between chips, and the panel opening rightward whatever edge the floating bar docks to. Agents come grouped by project, one rule between groups and no heading — the column is too narrow for one, and a chip's own panel names its project. There is no window to transform, so the sidebar's own logo expands the column and a chip click opens that chat in the conversation pane through the sessions store (a hold still reaches the panel), and the Studio entry raises the in-window Studio request: `requestStudio(studioEvent?)` (`src/client/studio-request.ts`) dispatches the `idealize:open-studio` document event, and `@idealize/ui-bar` answers it with the same Studio open it runs for the floating bar's `open-studio` feed event. A request may name one Studio event to land on, which is how an alert `@idealize/notify` raised opens the exact event it named. Three packages share that one stateless module (inlined into each bundle) and nothing else.

Every colour in `Askbar.module.css` is a theme token, so the bar follows the light and dark schemes with the sidebar: the sidebar fill (`--dsw-specific-sidebar-fill`) painted over the app ground (`--dsw-alias-bg-base`, which shows through when an appearance surface sets the fill transparent), label tokens for ink, the `border-l*` steps for rules, the brand accent for needs-input and unread, and the state tokens for wrong (error) and presence (success). `tests/askbar-css.spec.ts` reads the sheet and fails on any literal colour. Portrait fills stay literal in `portrait.ts`: they are the agents' identity colours, not theme surfaces.

All copy is in `src/client/locales.ts` (`idealize-askbar` namespace, English and Simplified Chinese), registered through `ctx.locale` and delivered to the components as the `t` seat.

The compact panel holds the design spec's six elements (revised 14 Sep 2026): agent and project (17px and 13px at the head, JJ's accessibility ask of 14 Sep 2026), the latest task, the agent's latest status line, the chat's recent exchanges, one ask field, and Open the Studio. The exchanges (JJ, 14 Sep 2026: "do something useful with the large blank space") are the last `RECENT_EXCHANGES` question-and-answer pairs from comm's `transcript` command, newest last, re-read every `RECENT_REFRESH_MS` while the panel is open and again after each send, so an ask made from the bar shows its answer where it was asked; a pair without an answer reads Working on it… while the agent runs. In the bar's own window the panel runs the column's height and the exchanges take the room; in the sidebar home they scroll inside a 220px strip so the card stays compact. The panel slides in from its chip over 160ms (`askbar-panel-in`, off under reduced motion). One panel shows at a time (JJ, 14 Sep 2026, minimode feedback): a hover that outlasts `hoverRevealMs` reveals it unlocked, with the ask field focused, and it follows the pointer from chip to chip; it closes once the pointer has been off both the chip and the panel for `PANEL_LEAVE_GRACE_MS` (250ms), so crossing the gap to the panel keeps it. A click or Enter locks it on that chip; the same chip clicked again, a press outside the panel and the chips, or Escape closes it, and another chip rolled over or clicked switches it to that agent while it stays locked. A hold's card takes the panel's place while the hold runs. In the bar's own window the room comes with the keyboard: `POST /idealize/askbar/focus { focus }` reaches `desktopActions.focusBar`, which focuses the bar's window while a panel shows (it is a non-activating panel, so the app behind stays frontmost) and blurs it when the panel closes, so typing returns to the app the person was in. The ask field's Send wears the composer send circle's paint (the `button-info` fill pair the appearance panel's action colour writes, white text in both schemes; JJ, 14 Sep 2026) and sends through `POST /idealize/comm` (`send` to the chip's session); the project cell expands to the main window through the transform route, and the Studio entry (with the panel's Open the Studio) also asks it for the Studio chat, which spans every project.

Press and hold runs the A5 gesture without audio: hold shows Listening (pulse ring, error-red border), release runs the one-second pending countdown with a progress bar, Escape discards, and completion opens the panel stating that voice capture arrives in A5. Every state animation has a reduced-motion fallback.

## Transform

`POST /idealize/askbar/transform` `{to: 'mini'|'maxi', open?: 'studio', project?}` (loopback + `x-idealize-auth: 1`) forwards to the desktop shell's `desktopActions.collapseToBar` / `expandFromBar`; without a composed desktop shell it answers 501 and moves no window. `open: 'studio'` pushes one `open-studio` event (carrying `project` as context when given) onto the host bridge feed before the transform, so the main window's client (`@idealize/ui-bar`) opens the one Studio chat — with or without a shell, which is why the push comes first.

`POST /idealize/askbar/width` `{width}` (same fence) asks the shell for the bar window's width in pixels; `AskbarRoot` posts it when a panel opens and again when it closes, so the window grows to hold the panel and shrinks back to the column, and `AskbarWindow.hide()` restores the resting width on its own.

## Hold to speak

Holding a chip records, transcribes and sends to that agent. The chip the pointer went down on is the destination for the whole flow: the roster may move underneath, and the transcript still reaches the agent the hold locked onto.

The phases, each one a card beside the rail: a first-use notice (what is captured and where it is processed), **Listening** while the microphone is open, **Transcribing** while the seam works, **Preparing** with a percentage the first time the model is fetched, then a countdown showing the words before they go, and **Sent**. Escape ends any phase — the microphone closes, the countdown stops and nothing is delivered.

The audio never leaves the machine and never reaches disk. `@idealize/askbar/src/client/capture.ts` records, decodes and resamples to 16 kHz mono in the window, and what crosses to the host is float samples. `@idealize/transcribe` runs whisper there, on this Mac.

A transcript the provider cannot vouch for — empty, or only a non-speech marker — opens the panel holding the words instead of sending them, and so does a send comm refused, so a capture is never lost to a failed delivery.

The notice is remembered in this window's storage under `idealize.askbar.speechNotice`; cleared storage shows it again.

## Configuration

All timings are config fields (`idealize-askbar`): `edge` (default `left` — JJ, 1 Sep 2026), `hoverRevealMs` (150), `pendingSendMs` (1000 — JJ, 1 Sep 2026), `transformMs` (200), `pollMs` (2000).

## Model Experience

None, as the package renders host state into a desktop window and forwards user input to `@idealize/comm`, whose mailbox copies own any tokens a panel send later contributes.

#### KV Cache effect

Independent: no model request is touched, so no prefix changes and no reuse is invalidated.

## Known Limitations and Deferred Work

- The Askbar window class, the transform implementation, the drag-position memory and the global shortcut live in the desktop repo; without them the transform route answers 501 and the bar renders in no window. A1 ships them together.
- `hoverRevealMs` is served but the hover destination card is not rendered yet; the panel (click/Enter) carries the destination in the prototype.
- The docked edge has two owners until the desktop view-state wiring lands: this package's `edge` styles the bar and panel side, and the desktop repo's `askbarSide` setting places the window. Both default left; changing one without the other splits them. A remembered drag position overrides the side for placement but not for the panel's opening side.
- The panel's "response summary" line is the agent's comm status label until Studio events carry per-task summaries (A3).
- `confident` is decided from the transcript's text, not from a likelihood the model publishes, so a clearly-spoken wrong word is sent without review.
- The speech notice is remembered in window storage rather than settings, so there is no way to read it again from the interface once it has been dismissed.
- A hold that begins while the model is still being fetched records anyway and waits at the Preparing card afterwards; there is no way to start that download before the first capture.
- The sidebar home's store runs from the moment the sidebar declares its rail seat, whether or not the column is collapsed, so the main window polls the roster and holds a hurry-up stream while the rail is not showing; starting it on the first collapse would spare that. With the rail seated, the project browser unmounts at the collapse settle and remounts on expand, so a search typed into it does not survive a collapse (it does in a composition without the rail).
- The Askbar window holds two long-lived loopback streams (the client runtime's connection stream plus this package's `/idealize/events/stream` hurry-up). Chromium caps HTTP/1.1 at six connections per origin, and the bar's pair helped exhaust it once Terminal chats added theirs; the desktop shell lifts the cap for loopback (`ignore-connections-limit`), so this is hygiene, not a fault — folding the hurry-up onto the runtime stream would spare one connection per window.
