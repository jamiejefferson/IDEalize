# @idealize/onboarding

First-run onboarding: a five-step, full-screen wizard — **set-up** (step id `agents`), **projects folder**, **documentation folder**, **skills folder**, **finish** — that runs ahead of the showcase tour on first launch. Every step can be completed or skipped individually, the whole flow can be skipped from the persistent "Skip setup" control, and each completed step celebrates with a rainbow burst and a toast line. Someone who updates into the three-view app (Chat, Coding, Studio) sees one welcome sheet, once.

## What the plugin does

- **Settings section `idealize-onboarding`** (host half) — `{ done, steps, completedAt?, simplerSeen }`: `done` closes the flow for good, `steps` records each step's `'done' | 'skipped'` outcome so a relaunch resumes on the first unresolved step, `completedAt` timestamps a completed run, and `simplerSeen` (default false, so a section stored before the field existed still validates) records that the person has seen the three-part set-up. The schemastery schema validates step keys against the step-id union, so a hand-edited `settings.yaml` with an unknown step fails the registration.
- **The set-up routes** (host half, loopback-fenced; the mutations demand the `x-idealize-auth` header) — `GET /idealize/onboarding/agents` reports Claude Code CLI detection (the subprocess seam's executable resolution, so a miss is a verdict, not an error), OpenRouter and fal credential presence, and the Terminal's default launch command; `POST /idealize/onboarding/openrouter` verifies a typed key against OpenRouter's models listing **before** anything persists (a rejected key stores nothing), then stores the credential and writes the `openrouter` provider route's only needed configuration — its `apiKeyEnv` binding — into the `llm-pi-ai` section.
- **The align route** — `POST /idealize/onboarding/align { cli? }` takes the id of one of the Terminal's launch choices (`claude-code`, `codex`, `gemini`, `antigravity`, `kimi`, …). It stores that choice's command as `idealize-ui-terminal.launchCommand` and, when an OpenRouter key is connected, writes the default chat model (`agent-default-model`) as a model of the same company on the `openrouter` route: `claude-code` → `anthropic`, `codex` → `openai`, `gemini` and `antigravity` → `google`, `kimi` → `moonshotai`. From the route's model list it prefers an id containing `haiku`, `mini` or `flash` for the first three companies, the most recently listed first by OpenRouter's directory; otherwise the cheapest model that states a price. `:free` variants never win. It answers `{ launchCommand?, defaultModel?, note? }`, where `note` says why a write did not happen (no key, no model of that company, no stated price, no company for that app). A `cli` naming no launch choice answers 400 and writes nothing. A chosen default also switches `idealize-models.mode` from `auto` to `manual`, as `POST /idealize/models/default` does.
- **The owl clips route** (host half, loopback-fenced) — `GET /idealize/onboarding/owl/<clip>.<hash>.webm` serves each clip as immutable `video/webm` with byte ranges, so the client bundle carries URLs alone; the hash in the file name comes from the clip's bytes, so a changed clip gets a new URL. Regenerate `src/owl-clips.ts` (bytes, host only) and `src/owl-clip-urls.ts` (URLs, both faces) with `pnpm tsx scripts/gen-owl-clips.ts "<OnboardingOwls/transparent dir>"`.
- **The wizard** (browser half) — one `shell.overlay` occupant (`idealize-onboarding`, order 95) renders an opaque full-screen panel per step: the per-step owl clip (transparent WebM, streamed from the owl clips route; parked on its first frame under reduced motion), a headline and one-line sub in en+zh, a six-dot progress indicator, Back / Continue navigation, a per-step "Skip this step" link, and the top-right "Skip setup". Each step body reports whether Continue may engage and registers its save-on-Continue action.
- **The set-up step** ("Set up your models", step id `agents`) — three numbered parts, each with one sentence saying what it unlocks. Part 1 is a radio list of coding subscriptions built from `GET /idealize/terminal/launches`: Claude (Claude Code), ChatGPT (Codex), Gemini (one row, which uses `agy` when Antigravity is installed and `gemini` otherwise) and Kimi behind a "Show Kimi" link; each row reads Installed or Not installed, the first installed row starts selected, and a row that is not installed cannot be selected. Part 2 takes an OpenRouter key and, once a subscription is selected, says which company's models Chat will start on. Part 3 takes an optional fal key (saved through `POST /idealize/brains/services`). A "Use a company key gateway" link reveals the gateway's address and key fields. Continue engages once a coding app is selected, an OpenRouter key is connected or pasted, or a gateway is connected; it saves the pasted keys, then calls the align route, and a refusal shows in place. "Skip keys for now" saves no key and still aligns the selected app.
- **The welcome sheet** — a second `shell.overlay` occupant (`idealize-onboarding-simpler`, order 94) shows once to a section with `done: true` and `simplerSeen` not yet true, never while the wizard shows. It says what changed, reads Coding as Ready when the Terminal's launch app is installed and Chat and Studio as Ready when an OpenRouter key is connected, and otherwise shows the same parts as the set-up step for what is missing (the fal block while no fal key is connected). When no OpenRouter key is connected and the default chat model's service is connected (`GET /idealize/models/state`), it says Chat keeps working on that service. "Save and continue" saves the pasted keys and calls the align route only for a coding app chosen in the sheet; "Not now" saves nothing. Either button writes `simplerSeen: true`. Finishing or skipping the wizard writes it too, so a new install never sees the sheet.
- **The folder steps** — each captures one folder through the Host directory picker or a typed path, probes it live through `POST /idealize/setup/alias` (a successful probe also persists the alias; orientation re-confirms at finish), renders the probe's refusal verbatim, and gates Continue on a successful probe of the current path. An existing `idealize-setup` alias pre-fills the field, so a returning user confirms in one tap. The skills folder step (JJ, 15 Sep 2026) captures the `skills` alias the same way; its folder is stored at the probe and never re-confirmed by orientation, which stays on the two folders the first project needs.
- **The weekly review offer** (JJ, 16 Nov 2026) — once the documentation folder passes its probe, the documentation step shows one unticked box, "Review this folder every Monday at 08:00", with a line saying what the review does and that it never renames or deletes a note. Continue calls `POST /idealize/setup/weekly-review` only when the box is ticked; a refusal renders in place and the step stays until the box is cleared or the call succeeds. When `GET /idealize/setup/weekly-review` reports the review accepted and switched on, the step says so and shows no box. `@idealize/setup` owns the review itself.
- **The finish step** — the optional first-project name (locale default; omitted when emptied), then Continue runs `POST /idealize/setup/orientation` with a progress line, renders a 400's per-field refusals verbatim, selects the created project, and completes the flow (final burst, `done` + `completedAt`).
- **The Settings re-run row** — a `settings.general.item` row ("First-run setup") resets the section to `done: false` / `steps: {}` so the wizard re-arms on next launch.
- **The rainbow burst** — every step completion fires a full-screen, click-through celebration: expanding conic rainbow rings over a soft radial flash plus the per-step toast ("Agents connected!", …), pure CSS keyframes over ~800ms. Under `prefers-reduced-motion` the rings swap for a brief static tint; the toast stays. Skips never celebrate.
- **Tour sequencing** — the plugin takes `ctx.tour.holdFirstRun()` at start and releases it exactly once when the flow closes (finished, skipped, already done with nothing to show, the welcome sheet closed, or settings unavailable on a remote browser), so the showcase tour fires as onboarding's final step through the tour's own first-run trigger. (`@idealize/setup`'s client overlay, the previous hold-holder, is retired — this package is now the wizard's only surface.)

## Model Experience

None, as the wizard writes settings, credentials, the Terminal's launch command and the default chat model through host routes; the chats that later run on those choices own every model-facing effect.

#### KV Cache effect

Independent: nothing here enters a chat request. The default chat model written by `POST /idealize/onboarding/align` changes which model later requests go to, not any request's prefix.

## Known Limitations and Deferred Work

- The alias route doubles as the folder steps' probe, so a successful probe persists the alias before the finish step's orientation re-confirms it; a user who abandons the wizard between a folder step and finish keeps the probed alias.
- The services route states no fal model count, so the fal part's sentence names none; the client reads an optional `modelCount` on the fal row and uses it when the route starts to state one.
- Nothing can detect whether a coding app is signed in, so the set-up step reports installation alone.
- The align route reads listing dates and prices from OpenRouter's directory at call time; when the directory cannot be read, a hint-word match falls back to list order and a company without a hint word (Kimi) keeps the standing default.
- The welcome sheet aligns only a coding app chosen in the sheet, so someone whose Coding row already reads Ready and who adds an OpenRouter key there keeps their standing default chat model.
- The re-run row resets the seed for the NEXT launch — the gate decides once per session, so a reset mid-session does not re-open the wizard in place.
- The owl clips' ~635KB of WebM rides the host bundle as base64 (`src/owl-clips.ts`); each clip decodes on its first request, and the client bundle must never import that module.
