# @idealize/ui-bar

The IDEalize tool rail and everything it opens, both halves. The browser renders the 48px icon column on the frame's `shell.rail` seat, its panes in the docked `shell.drawer` column, the file viewer in the `shell.deck` column, the welcome card that starts every chat, the pinned Studio card at the top of the sidebar, and three composer occupants. The host serves the loopback routes the Files pane and the file viewer read. Mounted by the `idealize` profile as the `idealize-ui-bar` row.

## The rail and its panes

Every rail entry opens a pane in the drawer column at the window edge, so nothing covers the conversation and no rail entry opens a modal. `BarPanel` (`src/client/bar-store.ts`) names the eight panes:

| Pane | What it hosts |
|---|---|
| `files` | Two rows of tabs over the fenced listing routes below: the first picks whose files show (This project, All projects, Skills), the second which of their two folders (Project files or Documentation; All project files or All documentation). This project's documentation is the folder the vault resolves for the project until the user picks another with Change folder (`POST /idealize/setup/project-docs`); All documentation is the vault plus any chosen folder outside it. Under them sit a collapsed browse pane, create file and folder, Reveal in Finder, Add to chat, and Reconnect for an alias whose folder has gone. A clicked Markdown file or image opens in the deck's viewer; any other file opens in its default macOS application (`POST /idealize/bar/open`), and in the viewer where the host has no launcher or refuses the file, with Open in IDEalize on the row menu. Each view opens on its folder's contents: the toolbar names the folder and the tree lists it straight away, with no root row repeating the name (a lone root's drop zone and folder menu move to the tree background; several project roots keep their own rows, open until folded). Clicking a file opens it in the deck's viewer. A reveal request (`revealFile`, below) opens the way down to one file and lights its row. Rows drag: onto a folder in either tree as a move (`POST /idealize/bar/move`), onto the composer card as Add to chat (the `application/x-idealize-path` payload; `text/plain` rides along). The row menu offers Open, Add to chat, Reveal in Finder, Copy path, Idealize this and New file/folder here (folders), Rename…, Duplicate and Move to Trash; Idealize this registers the folder as a Workspace and opens a chat in it, and is idempotent on the path, so a folder that is already a project opens the one it has; Trash goes on its second click and appears only where `GET /idealize/bar/capabilities` reports `trash` (the desktop shell's trash action, or the Finder on macOS). |
| `terminal` | A plain shell for running commands beside a chat: `@idealize/ui-terminal`'s grid over one bare shell (`ctx.terminalMode.Pane`; no launch command, no chat), painted like the main Terminal view. The rail shows the entry, under Files, only once the terminal service reports an embedded terminal (the desktop shell), and the entry leaves with the service. The shell starts in the current chat's project (else home) the first time the pane opens and keeps its scrollback across close and reopen. |
| `hatch` | The Service hatch: a full chat surface over a real agent session rooted in IDEalize's own source checkout (Service tab), and `@idealize/hatch`'s composition page (Composition tab). The Service banner carries the source path with an in-place edit persisted through `POST /idealize/hatch/service`; the movie quote opens the transcript as an animated chat row (typing indicator, then the line). |
| `models` | Brains: the brains grouped by the space they work in (Chat, Terminal, Images, Sounds, Video, in the order `GET /idealize/spaces` serves them), each row stating its model as text in a `data-brain-model` span (the override's id, or "Default · <resolved id>" while it follows the default; a brain confined to one generating space states that space's generation model by name from `/idealize/brains/media`, or the candidate a generate call falls to) with the edit sheet as the one place a model is chosen (JJ, 7 Sep 2026); a brain whose chat route has no stored key is marked from the agents route's `access` with an Add key action, and one whose route is a subscription nobody has signed in to reads "Not signed in to <route>" with a Sign in link to `/idealize/signin`; a generating space's own model row titled by what it makes (Images, Sounds, Video) only while no brain states it, the media refusal's Add OpenRouter key action only while the route's `keyMissing` says a key is what is missing, agent roles below (the Project Coordinator row is the role; which preset plays it stays in `@idealize/comm`'s settings and the pane offers no second picker for it), an in-pane edit sheet asking spaces, then model (`data-brains-model`, listing providers and models alphabetically, every provider named by one rule — the directory's name when it is one, else the id with a capital — with a `data-brains-model-filter` search field once the catalogue passes 40 models and a `data-brains-catalogue` note stating how many models from how many services the lists hold and when they were read, or that nothing matches the typed filter; a generating brain is asked two: the generation model from that space's capability-compatible candidates, and the chat model that drives its generation tool, `data-brains-chat-model`, saved as the brain's own override), then instructions; every save raises the `idealize:brains-changed` document event, on which the welcome card reloads its roster and access map; a Models tab re-hosting upstream's Models settings page through `ctx.modelsSettingsSection`; a Budget tab over `@idealize/models`' usage route, whose table cells lead with the cost the host computes from known token prices and subscription plan costs (token counts beneath; notes name any unpriced usage the costs leave out, and with nothing known the cells stay token-only under a hint — costs are never estimated), followed by a Models this month table (`data-spend-models`): one row per model with usage, its tokens, and its cost where a metered route has a price or a Set price action where it has none (subscription and free rows state their category); Under it a Generations this month table (`data-generations`) carries one row per generation endpoint (`data-generation-row="<endpoint>"`) in three columns: the endpoint id over the service's name and the media kind, the count of artefacts it made, and the cost fal billed with the units it charged for. A row fal has not billed reads “not billed yet”, and the total line sums the billed rows in fal's own currency. With no fal key stored the section asks for one (“Connect fal to see what generations cost.”); with a key and nothing generated it reads “No generations this month.”; a refused read shows fal's own message. A brain whose route a terminal CLI serves (the `terminal` rows of `GET /idealize/activity/agents`) reads "Runs as the claude CLI in the terminal, on its subscription. The Terminal group's rows carry a CLI picker over `GET /idealize/terminal/launches`' catalogue (per-brain override, plus a Default CLI row), written through `POST /idealize/terminal/launch`; only CLIs the login shell finds are offered, a stored choice of a missing one stays visible marked "not found on this Mac", and the pickers render only where that route serves a catalogue, which is the desktop app. |
| `trajectory` | The event ledger, re-hosted from `ctx.trajectorySection` and the receiver of the chat's "inspect this call" handoff. |
| `schedule` | The Week calendar, re-hosted from `ctx.scheduleSection` (`@idealize/ui-schedule`). |
| `feedback` | The feedback form, posting to `@idealize/feedback`'s submit route. |
| `appearance` | `@idealize/appearance`'s inspector; the bar mirrors that service's own open flag both ways, so ⌘⌥A and `ctx.appearance.open()` land in the same pane. |

The rail reads top to bottom: Files, Schedule, Trajectory, Brains (a two-star sparkle glyph, JJ 3 Sep 2026), Plugins (only while the market launcher is mounted), Appearance, Feedback, Service hatch (JJ, 2026-08-28). The collapse-to-Askbar button (mini mode, JJ 2 Sep 2026: the Askbar IS mini mode) is not a rail entry: `MinimodeButton` occupies ui-sidebar's `sidebar.header.action` seat, left of the collapse toggle, posts `POST /idealize/bar/minimode`, which calls the desktop shell's `collapseToBar` action (the main window glides into the bar, no restart), and renders nothing while `GET /idealize/bar/capabilities` reports no desktop shell.

The bar's view state (open pane, hatch tab, deck file, a pending Brains request, a pending inspect target, a pending Files reveal) lives in one snapshot store whose only writer is the plugin body, so the pane can be driven from outside React.

## The pinned Studio card

Studio is not a rail pane (JJ, 3 Sep 2026: "it's like the lead agent in v0", "the studio is for all projects"): `StudioCard` occupies ui-workspace's `sidebar.workspaces.pinned` seat, the strip above every project, without a toggle or a dismiss because the Studio is open at all times. It reads as one more chat row (JJ, 8 Sep 2026: "it should have the same look as other chats but with a subtle rule between it and the projects"): the named session row's 44px height and radius, the Studio icon `@idealize/spaces` serves in the rows' 16px lane, a 13px title over an 11px line reading `Telegram - Connected` or `Telegram - Not Connected` (JJ, 15 Sep 2026; connected once `@idealize/telegram`'s status route answers a stored token, a paired chat and no standing problem, read on the same poll as the overview; a refusal, an absent host or a composition without the row reads as not connected), transparent until hover, and the rows' `interactive-bg-hover` fill while the Studio chat is the open chat (`data-current`), so an unselected Studio no longer looks selected. Its own wrapper (`data-studio-card-wrap`) draws a 1px `border-l2` hairline 8px under it, the rule before the projects; the pinned strip itself is upstream and untouched. A green dot says `@idealize/studio` answered the last overview read, an accent count sums the events past each project's read position (`@idealize/notify`'s ledger) and a warning count sums the tasks holding unresolved attention across every project — two records, two marks: reading the Studio clears the first and resolves nothing (FR-P0-19); it polls the shared Studio store (`ctx.studioSection.store`) every 3 seconds while mounted so both stay live whether or not the Studio view is on screen, and renders nothing while no project exists to hold that chat.

Pressing it opens the one Studio chat: an existing chat in the `studio` space that a listed project still holds is opened (a Studio chat left behind by a removed project has no workspace, so it is left where it is; should such a chat be shown anyway, `HeroLauncher` renders nothing for a `studio`-space chat without a project rather than the project chooser, since the Studio runs across every project and no one project is the answer); otherwise `connectWorkspace` supplies a blank chat in the first listed project, `noteLaunch` tells the seed, the chat opens, `POST /idealize/spaces/select` records the space, and the ring lands on the `studio` view. The open comes before the record because `connectWorkspace` hands back the project's existing blank chat when it has one, and after a restart the host has no live session of that id: the route answers 404 until the open resumes the chat, so the record retries across the resume (20 attempts, 250 ms apart) rather than being dropped. Until the record reaches the projection, `SpaceSeed.launchedSpace` is what answers "which space is this chat in" for the card's current mark, the reuse scan and the welcome card, so a chat launched here never shows the space chooser. The welcome card treats a `studio`-space chat as launched, so the chat keeps the ordinary composer under the Studio view; the tree hides the chat (`@deepseek-ai/dsh-client-ui-workspace`) and New chat's blank reuse skips it (`@deepseek-ai/dsh-client-runtime`). The Askbar's Studio entry reaches the same open two ways: the floating bar through the host bridge feed (the plugin listens on `/idealize/events/stream` from the retained tail onward and opens the Studio on an `open-studio` event), and the sidebar rail through the in-window `idealize:open-studio` document event (`@idealize/askbar`'s `studio-request` module, inlined here as the galleries' Reveal signal is). A request may name one Studio event — an alert `@idealize/notify` raised and the person opened does — and the open hands it to `ctx.studioSection.store.focus` first, so the view lands on that event.

## Services

A landed artefact (`onArtefactLanded` from `@idealize/artefacts`) bumps `filesReload` in the bar's view state and the Files pane re-lists every folder it has loaded, so a new folder such as the first video's `Video/` shows without pressing Refresh (JJ, 16 Sep 2026: "the file listing didnt refresh to show the new video folder"). `ctx.idealizeBar` (`IdealizeBarService`) is the cross-plugin face: `state` (read-only), `show(panel)`, `close()`, `openFile(path)`, `closeFile()`, `revealFile(path)`, and `addBrain(space)`, which opens the Brains pane on its add flow with the space already set. `revealFile` opens the Files pane on one absolute path: the view whose root holds it (narrowest first: project files, the project's documentation, all project files, all documentation, skills), every folder down to it expanded, its folder made the creation target, and its row scrolled into view and lit (`data-revealed`) until the next click or four seconds; the request lives in the view store as `reveal {path, nonce}` until the pane has shown it, and a path under no tab leaves a status line saying so. The galleries reach it without importing this package: a tile's **Reveal** raises `@idealize/artefacts`' `idealize:reveal-artefact` document event with the artefact's project-relative path, and the plugin resolves that against the active chat's project root (the workspace holding the chat, else the chat's cwd) before calling `revealFile`; with no chat open it logs a warning and does nothing. Calls go through the same closures the rail's own entries use, so a shell without the rail (the desktop mini frame) drives the same panes and the drawer, deck and appearance state cannot fork between hosts.

The plugin injects `modelsSettingsSection`, `trajectorySection`, `scheduleSection`, `studioSection` (its store feeds the card) and `appearance`, each a Context service carrying a component plus a wired face. This is the sanctioned channel: the client bundle purity gate forbids cross-plugin value imports, so a pane cannot import another plugin's component. `terminalMode` (`@idealize/ui-terminal`), `idealizeNotify` (`@idealize/notify`) and `workspaceAliases` (`@idealize/setup`) are probed with `ctx.get` and tolerated absent.

## The welcome card

`HeroLauncher` fills the hero composer card's `conversation.hero.launcher` seat at priority -1 and asks two questions in order, both from one `GET /idealize/spaces` payload so a tile's count and its brain list never disagree. Step 1, which space: five tiles in the declared order, each carrying its brain count, none ever dimmed or disabled; pressing a tile advances to step 2, except when exactly one brain works in the space, a model can serve it and that brain's row would start the chat (its `access` reports no refusal; in Terminal the CLI runs on its own login, so access does not apply): then the tile starts that brain at once (JJ, 7 Sep 2026: "skip the brain selection if there's only one brain"), the card root carries `data-launcher-autostart="<brain id>"` for the round-trip, and a host that refuses drops the card onto step 2, which shows why. A lone brain whose route wants a key or a sign-in still gets step 2, so the step can explain. Step 2, which brain: the brains that work in the chosen space, each row a button that starts the chat; a brain whose chat route has no stored key (the agents route's `access`, read through `LauncherSpaces.access`) says so and opens the key editor instead, because a chat on it fails at its first turn. In Terminal each row names the CLI the brain launches instead (`LauncherSpaces.terminalLaunches`, the `GET /idealize/terminal/launches` table Brains edits: the per-brain override or the default, labelled through the catalogue, `''` reading "Plain shell"), and the chat-model key gate does not apply, because the CLI runs on its own login (JJ, 2 Sep 2026: the step showed a model and the shell launched a different CLI); a CLI the login shell does not find is stated on the row. Step 2 has three states driven by the roster entry alone: brains listed; no brains but a model can serve the space, offering "Add a brain for <Space>" through `addBrain`; no model can serve it, stating the route's reason with the shared recovery sentence, the add-key action only where a key is what is missing (`no-model`, or `no-compatible-model` with `keyMissing`), and the way back. A launch records the space and brain through `POST /idealize/spaces/select`, recomposes the chat's preset (an activity brain through `@idealize/activity-pills`' `activityPills` service so the free-tokens route and the roster default keep one owner; any other brain for this chat alone, followed by its roster model through `sessions.selectModel`, since the preset carries none), then flips the view ring or, for Terminal, calls `terminalMode.open`. The card counts a chat with a recorded brain as launched, so a reload does not ask again. Without a project the card offers recent projects, New project and Find a folder instead.

## Reading and writing the view ring

`view-switch.ts` reaches a chat's conversation store through the slot registry's renderer host face, the same instance the rendered ring reads. `createSpaceSeed` seeds each chat's `view` from its `space` projection once per chat per page, the first time the chat is current and its projection, the chat ring entry and the store instance all exist; a space whose view the ring does not serve (Motion everywhere, Terminal in a plain browser) lands on Chat. A launch beats the projection: the card calls `noteLaunch(sessionId, space)` before it writes the record, so the seed cannot take a relaunched blank chat back to the space its projection still names, and a launch whose own ring write found no entry is placed by the next ring change. It also watches the chat store's `inspect` field and opens the Trajectory pane on the clicked call. The ring renders no tab row; the active view is written only by the welcome card's launch, `terminalMode`, and this seed.

## Composer occupants

`HeartButton` on `conversation.input.right` (order 10) submits the thank-you message as an ordinary turn when the draft is empty and stands down while a draft is being written. `PlanToggle` on `conversation.input.plan` (priority -1) runs `/plan` or `/plan off` through the command channel, so `dsh-plan-mode` stays the single owner of the state; it reads the ring's active view from the chat entry's store and renders on Chat and Terminal only (and before a view is chosen), and its tooltip names the mode before the click's effect ("Plan mode on. Click to turn off."). `NoPresetChip` shadows `conversation.hero.agentPreset` with nothing, because the brain step is the preset choice. `HatchTrigger` shadows `settings.trigger` with an empty occupant so the sidebar foot hides its Settings button. `NoLanguageRow` shadows the General settings' `language` row with nothing, and the plugin pins the active locale to English whenever it moves (JJ, 16 Sep 2026: "no deepseek refs or chinese language in the product"), because the upstream locale plugin keeps its Chinese dictionaries, its browser detection and that row. `NoProviderDialog` shadows every settings onboarding entry other than the `welcome-notice` the same way, as each appears, because the upstream entries are provider key dialogs and the product's models come through OpenRouter and the keys file; the ids come from the slot, so the code names no provider. The composer's "+" menu (`ctx.composerMenu`, probed like the settings opener) gains three entries from this package. `Skills & Commands` (order 10, JJ 15 Sep 2026: "a skills chooser in the modal that uses the skills folder as its source", "blended … Skills & Commands") reads `GET /idealize/bar/skills` and the session's `commands.list` every time the menu opens and lists them under headings behind a search field that matches names and descriptions: one heading per folder of the catalogue (the skills folder itself as "Skills folder", then each subfolder under its own name, JJ 15 Sep 2026: "i need subdirectories for the models to use"), then Commands; a package the registry did not accept (an invalid name, a manifest that does not parse) is listed but disabled, and a name listed in two folders inserts the same `/name` reference, which the registry resolves to the first folder by name; the wider catalogue (`~/.agents/skills` and the rest) stays with the typed `/` menu (JJ, 15 Sep 2026: "anything in agent/skills is only accessed by the / command as those are model specific"): a skill pick inserts `/name ` into the draft, a bare command runs at once through the command channel as the `/` menu does, and a command that takes input is inserted for the person to finish; the entry declares `commands: true`, so the bar drops its own Commands row. `Connectors` (order 20) opens the settings dialog when one is seated, where the Telegram pairing lives, and `Plugins` (order 30) clicks the mounted community market launcher, falling back to the hatch pane. Neither has a submenu, and neither names the service hatch (JJ, 15 Sep 2026: "this will confuse people").

## The deck viewer

`FileViewer` renders the fenced envelope and carries Add to chat and Reveal in Finder as header icons. A complete text envelope offers Edit: a plain textarea over the file's text, Save (⌘S) through `POST /idealize/bar/write` with the loaded size, Cancel discarding. A 409 (the file changed on disk) keeps the editor and its text up and says so; closing the editor reloads. A truncated read offers no Edit, because saving it would truncate the file.

## Host routes (loopback only; mutations need `x-idealize-auth: 1`)

- `GET /idealize/bar/capabilities`: which optional destinations exist here (the desktop shell's terminal, macOS reveal, macOS default-application launch as `openExternal`).
- `GET /idealize/bar/files[?path=]`: the workspace roots, or a directory's entries fenced to the registered workspace roots plus the captured alias folders (realpath prefix check).
- `GET /idealize/bar/skills`: the skills folder's catalogue from `ctx.idealizeSkills` (`groups`, each `folder` and its `skills` with `name`, `description` and `invocable`), where `invocable` is whether the host skill registry lists that name as user-invocable from the provider `@idealize/skills` mounts; empty `groups` without the service, and nothing invocable without a registry.
- `GET /idealize/bar/aliases`: the Files pane's four alias-backed folder sets (`tabs`) with their live access state, plus `projectDocs`, one entry per registered project naming its documentation folder, how it was decided (`chosen`, `note`, `name`) and its access state (`unset` while there is none). The listing fence includes every chosen documentation folder. The skills tab browses the `skills` alias, the folder `@idealize/skills` mounts into every chat's skill catalogue.
- `GET /idealize/bar/browse[?path=]`: the browse pane's listing, fenced to home plus the workspace roots plus the alias folders.
- `GET /idealize/bar/file?path=`: file content for the viewer as a size-capped JSON envelope; `GET /idealize/bar/raw?path=`: raw image bytes for the viewer's image tags, image extensions only; both under the home-plus-roots fence.
- `POST /idealize/bar/minimode`: collapse the main window to the Askbar through the desktop shell's `collapseToBar` action; 409 without a shell that has the bar. `POST /idealize/bar/terminal`: open the desktop shell's terminal when its action service is composed. `POST /idealize/bar/reveal`: reveal a fenced path in the Finder. `POST /idealize/bar/open`: open a fenced file in its default application through `/usr/bin/open` (macOS only, 409 elsewhere); 422 for a folder, a file macOS would run (`.command`, `.app`, `.scpt` and their kin, or an extension-less executable) and a type no application claims. `POST /idealize/bar/create`: create one file or folder inside a fenced parent, the name a single validated path component. `POST /idealize/bar/write`: overwrite a fenced text file, refused with 409 when its size no longer matches the `expectedSize` the editor loaded. `POST /idealize/bar/rename` (one validated component, 409 on a taken name), `/duplicate` (`name copy`, `name copy 2`, …, folders recursively), `/move` (into a fenced folder, never into itself, 409 on a taken name) and `/trash` (the desktop shell's `trashItem` action when composed, else the Finder on macOS with its one-time automation prompt; the item can be put back). Every path resolves through the home-plus-roots fence.

## Model Experience

### The thank-you turn

#### What the model sees

One ordinary user message, the `heart.message` dictionary value, submitted through the conversation input when the heart is pressed with an empty draft.

##### The thank-you message

```markdown
🩷 Thank you!
```

#### Token effect

One short user turn per press, and the assistant reply it invites; nothing is added to any other request.

#### KV Cache effect

Append-only: the turn follows the existing request prefix and invalidates nothing.

### Add to chat

#### What the model sees

The Files pane's Add to chat (its row action, its menu, a row dropped on the composer card, or the viewer's header icon) appends a file path and a trailing space to the composer draft; the path reaches the model only when the user submits that draft as their own message.

#### Token effect

The length of the path inside one user message; zero until the user submits.

#### KV Cache effect

Append-only, as part of an ordinary user turn.

## Known Limitations and Deferred Work

- **The view seed and the inspect handoff depend on a TS-private slot face.** `hostFace().storeOf` is the only way to resolve the per-session chat store the ring reads; if upstream publishes a per-session store resolver, `view-switch.ts` moves onto it.
- **The Service hatch's agent edits the running app.** Changes it makes take effect only on restart, and a restart ends every open chat including the hatch's own; the pane states this and does not restart anything itself.
- **Every Files listing probes each alias.** A `stat`, a `readdir` and a throwaway dotfile per alias per listing keep the Reconnect state live; a slow network folder slows the whole tree.
- **The rail's launch beat is timed in three places.** The rail keyframe in `IdealizeBar.module.css` must stay in step with `@idealize/ui-launch`'s `LAUNCH_SEQUENCE_MS` and its sheet delays; each carries a comment naming the others.
