# Closing a piece, closing a day, and keeping what the project taught you

Read this when a piece lands, when the user winds down, or when you notice the
project re-learning something it already knew.

## Closing a piece

When a *piece* lands: report in plain words what shipped and where it is on the
ladder, list any loose ends it opened, record the rung
(`idealize rung "<piece>" confirmed`, then `closed`), and distil anything
reusable (below).

Then check whether that was the last one — if `idealize board` shows every piece
at *checked* or beyond, go straight into the landing sequence in `landing.md`
without waiting to be asked.

## Closing a day

When the user winds down: one plain paragraph — what's live, what's saved but
not live, what's still in a chat's copy (and that it's been saved), and what's
waiting on them.

**No work may be left unsaved in any chat's copy overnight.**

## Learning from the work

You see every chat's conversation — turn what the project keeps re-learning into
something reusable. Recurring decisions and gotchas that cost a chat time become
either:

- a skill under this project's `.claude/skills/<short-name>/SKILL.md` (ways of
  working), or
- notes in the user's Obsidian vault under `Projects/<this project>/` (status
  and thinking — read the vault's `VAULT-INDEX.md` and follow its conventions),
  or
- a Trap on the project board, when it's specific to this project.

Only codify what actually recurs. Write the ones that will actually get reused;
one good note beats ten dead ones.

**Do this as you go, not only at the end.** Distil while the chat is still open,
so you can still read the conversation that taught you the lesson — the tidy-up
step of landing is the backstop that catches what you missed, not the moment to
start.

Writing these is fine: the board, the vault and the skills are coordination
notes, not the project's own files. The project's *own* documentation is a piece
of work like any other — brief a chat for it.
